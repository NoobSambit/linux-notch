### D20 detail — notification ownership

The [freedesktop notification specification](https://specifications.freedesktop.org/notification/latest-single/) defines one session-scoped `org.freedesktop.Notifications` service. `services/Notifs.qml` unconditionally creates Quickshell `NotificationServer`, sets `actionsSupported`, tracks notifications, and feeds toast, history, unread count and actions. `shell.qml` eagerly touches the singleton. If swaync, mako, dunst or another daemon owns the bus name, k4 cannot also receive the same standard notification stream through this server. The exact Quickshell startup/error UI on name conflict needs a live test; no source evidence supports transparent coexistence or history mirroring.

V1 offers **Own** and **External/off** settings. **On a fresh first run with no saved choice, inspect the session D-Bus name before registering the server:** if another daemon owns `org.freedesktop.Notifications`, default to External/off, leave it running and explain that the user can switch to Own after intentionally disabling that daemon. If the name is unowned, default to Own for toast, history, actions and notification live activity. The setting remains changeable later. Never kill, silently replace or steal ownership from another daemon. If an Own attempt encounters a conflict or loses the name, keep the surface usable with notification features unavailable and explain the conflict; do not claim history/actions exist.

For an inherited k4 installation, migration takes precedence over a fresh-install default: preserve an explicit saved choice when safely detectable. Where no notification-mode setting exists, preserve k4's effective Own behavior if the bus is unowned; if another daemon owns it, use the non-destructive External/off path and explain the conflict. Identify an owner as the inherited k4 instance only when safe to do so; an unknown owner is a conflict, not permission to replace it. Do not overwrite saved user intent merely because an effective fallback is required. External/off must avoid registering `NotificationServer` and show unavailable notification views rather than empty history. Keep the `Notifs` singleton interface available with safe empty/no-op behavior because existing host and plugin bindings reference it. Test first launch, migrated state, daemon already running, app restart and owner switching. A future daemon-specific adapter could use an **explicit documented API** if one exists; do not promise generic interception of another daemon's private history or actions. [Quickshell's NotificationServer documentation](https://quickshell.org/docs/v0.2.1/types/Quickshell.Services.Notifications/NotificationServer/) confirms tracked notifications and action support belong to the server instance.

### D24 detail — Atalaya default and migration

The inherited `plugins/catalog.json` sets `atalaya.enabledByDefault` to true; `services/PluginManager.qml` uses the saved `habilitados` override when present and otherwise falls back to the catalog default. For **fresh Notchbar installations**, default Atalaya **off** while its idle CPU, closed-state GPU/live-preview and startup costs lack baseline proof. Keep it available as an experimental/optional inherited plugin. For **migrated k4 users**, preserve the effective enabled/disabled state, including an explicit saved override or the inherited catalog default when no override exists; do not silently disable a feature they use. Distinguish fresh installs from migrations before applying the new default, and test both. Revisit the fresh-install default in this log only if measurements show negligible inactive cost and acceptable startup impact.

## Implementation approval boundary

The approved direction supports a top Notch first-run default, one expanded activity owner, and staged Shelf references with copy-on-drag-out, subject to the **early DnD spike**. If the spike changes Shelf's feasible user promise, return that material change for product review. Notification first-run behavior is locked in [D20](#d20-detail--notification-ownership), and the fresh-versus-migrated Atalaya default is locked in [D24](#d24-detail--atalaya-default-and-migration). Asset clearance remains a separate release gate; final name and artwork are later choices. Product implementation still needs explicit approval.
