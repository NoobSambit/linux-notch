# ADR-lite decision log — architecture approved, v1 product scope proposed

Research basis: [k4 audit](RESEARCH_K4.md), [Droppy research](RESEARCH_DROPPY.md), [feature matrix](FEATURE_MATRIX.md). D01–D03 and D09–D12 reflect the approved architecture direction; the expanded product scope and defaults below remain proposals. No implementation authority is implied. Revisit conditions let measured evidence change a proposal.

| ID / Decision | Reason | Alternatives considered | Trade-offs | Revisit condition |

| D01 — Keep Qt 6/QML/Quickshell | k4 already has broad functioning Linux services and plugins in this stack; no blocker found | GTK/Flutter/Electron/Rust/C++ rewrite | Retains Quickshell version and QML runtime constraints | Reproducible blocker in required v1 mode that cannot be addressed in stack |
| D02 — V1 only Wayland + Hyprland | Matches k4's real compositor integration and product lock | GNOME/KDE/Niri/Sway/X11 in v1 | Narrow audience now, less speculative work | After Hyprland v1 acceptance and a new compositor-specific evidence pass |

| D04 — Four named presentation modes | Dock and hybrid already exist; detached island fills form gap | Single adaptive mode with many toggles | Mode labels add settings complexity; migration must be safe | Usability test shows modes confuse users more than independent controls |
| D05 — V1 top/bottom polished, existing sides retained | User lock and simplest geometry/focus test matrix | All four edges equally polished | Side modes may look less refined initially | Existing side behavior regresses or user research shows high demand |
| D06 — Shelf plus clipboard, interaction and live-activity workflow polish in v1 | Shelf fills a missing handoff; clipboard and activity behavior already have k4 foundations but need substantial UX improvement | Shelf alone; large Droppy feature suite | More coordinated work across shell, dock and settings; needs strict acceptance gates | Hyprland DnD proof fails or user testing shows a proposed workflow harms daily use |

| D10 — Narrow `CompositorBackend` at repeated seams | Hyprland imports/commands span window, monitor, workspace and focus modules | Wrap every service; no abstraction | Some Hyprland-specific feature UIs stay specific | A second compositor implementation demonstrates a different seam is needed |
| D11 — Keep desktop services independent of backend | MPRIS, PipeWire, NetworkManager, BlueZ and files are not Hyprland APIs | Funnel all through `DesktopBackend` | Several service APIs still vary by installation | Evidence of a cross-desktop service mismatch requiring one adapter |
| D12 — Local-first, no telemetry, explicit network controls | Product direction and sensitive clipboard/file context | Silent convenience lookups, cloud by default | Weather/agent convenience may require one more setup step | User explicitly authorizes a network-first feature with privacy design |
| D13 — Separate settings window, morph daily activity in one surface | k4 settings/editor focus needs justify separate windows; daily HUDs benefit from continuity | Force every feature into pill; use unrelated popups for everything | More surface rules to test | Accessibility or performance tests show morphing harms usability |
| D14 — Preserve inherited functionality by default; evidence may justify individual removal | Broad k4 functionality is an asset, but dead, redundant, broken, unsafe, rights-incompatible, unmaintainable or product-harming features should not be immortal | Delete optional breadth wholesale; forbid all removal | Each removal requires evidence, user impact, compatibility plan and its own recorded rationale | New evidence changes a candidate's condition or product fit |
| D15 — Manual Hyprland installation baseline | V1 targets compositor, not distribution breadth | Distro-specific installers/package matrix | Some users will install dependencies manually | Usage evidence shows packaging is top release blocker |
| D16 — Distinct visual system begins before feature expansion | Core surface, dock, settings and new workflows need one vocabulary; product must not copy Droppy/Apple/k4 branding | Final cosmetic pass; immediate clone | Early token/component work adds design decisions before all features settle | Rendered trials show tokens cannot serve a required mode or accessibility need |
| D17 — Richer clipboard UX on current watcher/store first | k4 already has text/image history, search, pin and keyboard selection | Replace storage before UX work; leave clipboard as-is | File-reference offers may require later storage changes | MIME/source/security proof shows current architecture cannot support required v1 clipboard behavior |
| D18 — Small file-action contract inside Shelf | Open, reveal, copy path and remove make staging useful; future OCR/conversion/share can fit later | Build full tool suite now; hardcode only one-off buttons | Action model must stay simple and safe around missing files | Real user tasks demand richer actions or contract causes plugin compatibility issues |
| D19 — One expanded owner with explicit display policy | k4 already has per-screen surfaces but one global activity selection; v1 needs reliable hotplug/fullscreen behavior | Independent activity queues per display; primary-only surface | A cross-display expansion must rehome and return focus carefully | Multi-monitor tests show one owner cannot meet core workflows |

## Genuine input needed before implementation

1. **Approve or amend the expanded v1 scope:** Shelf, richer clipboard, interaction semantics, live activities, per-display behavior, small file actions and early visual-system work. This is the material product approval gate.
2. **Default first-run form:** recommend top Notch with an easy mode switch; Dock and Hybrid remain equally supported choices. Choosing Dock or Hybrid as the first-run default would change onboarding and priority screenshots/tests.
3. **Shelf ownership model:** recommend staged references with copy on drag-out and a visible missing-source state. Choosing managed copies at drop time would change storage, retention and privacy behavior. The feasibility gate may expose a technical constraint before this is final.

Preferred-display fallback can use the documented policy and be tuned during multi-monitor QA; it does not need a separate product decision now. Asset provenance remains a release gate: MIT source licensing alone does not establish rights to every embedded game/image asset. Final name and artwork remain later choices, not blockers for this scope review.

These questions can be answered together when reviewing the complete package. No broad consultation is needed for implementation details already resolved by source evidence.
